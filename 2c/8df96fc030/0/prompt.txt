This is a strong plan. The overall sequencing is right, especially the decision to stop after Phase 5 as the first meaningful landing point.

The main thing I would change is the boundary in Phase 1: I would not put `PushRefs()` / `FetchRefs()` directly on `CheckpointBackend`. That mixes archive semantics with transport semantics too early, and it will get awkward fast for `gmeta` and especially `S3`. I would split it like this:

- `CheckpointBackend`
  - `WriteCommitted`
  - `UpdateCommitted`
  - `ReadCommitted`
  - `ReadSessionContent` or `GetSessionLog`
  - `ListCommitted`
- optional `CheckpointSyncer`
  - `Push`
  - `Fetch`
  - maybe backend-specific ref sync operations

That keeps the core backend contract honest. `MultiBackend` can then fan out writes across mirrors without pretending every backend shares the same sync model.

A few other comments:

- Phase 1: good, but I would avoid “V1 and V2 implement via thin adapters” if that means wrapping concrete stores in extra boilerplate forever. If the adapter is just a temporary migration layer, fine. If not, you may be better off defining the interface around the methods they already naturally expose.
- Phase 2: good. Keeping `migrate` backend-aware is the right call.
- Phase 3: good and probably worth pulling slightly earlier if it reduces churn in Phase 2. The current session-state duplication is real technical drag.
- Phase 4: good product direction. I would be explicit that “default backend for new repos” and “automatic read precedence” are separate decisions.
- Phase 5: good, and I strongly agree with “mirrors don’t serve reads.” That keeps the model simple.
- Phase 6: good, but I would not gate this on line counts like “400 lines.” The real test is whether each extracted type owns one slice of behavior and has a stable dependency set.
- Phase 7: directionally good, but this is the riskiest and least urgent part, exactly as you called out.
- Phase 8: good cleanup, but definitely last.

Two things I’d add:

- Add a config migration phase or subtask.
Right now you move from:
  - `checkpoints_version`
  - `checkpoints_v2`
  - `gmeta`
to:
  - `backend`
  - `mirrors`
You should decide early whether old keys are still read indefinitely, auto-migrated on write, or warned about.

- Add a strict mirror policy.
Document whether mirror failures:
  - fail the whole operation
  - warn and continue
  - only fail in some commands
For `gmeta`, I suspect you want “primary success wins, mirrors warn.”

So my verdict is: good plan, with one substantial adjustment.

The adjustment is:
- make `CheckpointBackend` about permanent checkpoint storage
- keep sync/push/fetch as a separate optional seam
- then `MultiBackend` becomes much simpler and more durable

If you want the shortest path to a first implementation, I’d start by rewriting just Phase 1 in that shape before touching code.
