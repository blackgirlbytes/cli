# Fix Kiro CI auth: inject SQLite auth DB instead of SSO cache file

## Context

The previous commit wrote a token to `~/.aws/sso/cache/kiro-auth-token.json`, but `kiro-cli-chat` does **not** read from that path. Investigation shows:

- `kiro-cli-chat` stores auth in a **SQLite database** at a platform-specific path:
  - macOS: `~/Library/Application Support/kiro-cli/data.sqlite3`
  - Linux (CI): `~/.local/share/kiro-cli/data.sqlite3`
- The `auth_kv` table has two rows needed for auth:
  - `kirocli:odic:device-registration` — OAuth client registration (client_id, client_secret, etc.)
  - `kirocli:odic:token` — access/refresh tokens with expiry
- The `migrations` table must also be populated (kiro-cli-chat may refuse to use a DB without migration records)
- `kiro-cli-chat whoami -f json` validates auth is working

## Changes

### 1. Both workflows — replace "Inject Kiro auth token" step

Replace the current step that writes to `~/.aws/sso/cache/` with one that creates the SQLite database:


**Wait — SQL injection risk with `'$VAR'` in SQL.** The values are JSON containing single quotes potentially. Better approach: use parameterized inserts or base64-encode the secrets and decode in the step. Safest approach: write a small script that uses `sqlite3` with `.import` or heredoc-safe quoting.

Actually, the simplest safe approach: write the JSON values to temp files, then use `readfile()` or just read them in with a subshell. But `sqlite3` CLI doesn't have great parameterization. The safest approach for JSON that might contain quotes:

```yaml
  run: |
    mkdir -p ~/.local/share/kiro-cli
    DB="$HOME/.local/share/kiro-cli/data.sqlite3"
    sqlite3 "$DB" <<'SQL'
    CREATE TABLE IF NOT EXISTS migrations (id INTEGER PRIMARY KEY, version INTEGER NOT NULL, migration_time INTEGER NOT NULL);
    INSERT OR IGNORE INTO migrations (id,version,migration_time) VALUES (1,0,0),(2,1,0),(3,2,0),(4,3,0),(5,4,0),(6,5,0),(7,6,0),(8,7,0),(9,8,0);
    CREATE TABLE IF NOT EXISTS auth_kv (key TEXT PRIMARY KEY, value TEXT);
    CREATE TABLE IF NOT EXISTS state (key TEXT PRIMARY KEY, value BLOB);
    CREATE TABLE IF NOT EXISTS conversations (key TEXT PRIMARY KEY, value TEXT);
    CREATE TABLE IF NOT EXISTS conversations_v2 (key TEXT PRIMARY KEY, value TEXT, updated_at TEXT);
    CREATE TABLE IF NOT EXISTS history (id INTEGER PRIMARY KEY, value TEXT, updated_at TEXT);
    SQL
    # Use Python to safely insert JSON (avoids SQL injection from quotes in JSON)
    python3 -c "
    import sqlite3, os
    db = sqlite3.connect(os.path.expanduser('~/.local/share/kiro-cli/data.sqlite3'))
    db.execute('INSERT OR REPLACE INTO auth_kv (key, value) VALUES (?, ?)',
               ('kirocli:odic:device-registration', os.environ['KIRO_DEVICE_REG']))
    db.execute('INSERT OR REPLACE INTO auth_kv (key, value) VALUES (?, ?)',
               ('kirocli:odic:token', os.environ['KIRO_AUTH_TOKEN']))
    db.commit()
    "
    kiro-cli-chat whoami -f json
```

### 3. Secrets to configure

Two GitHub secrets needed (split for clarity and independent rotation):

| Secret | Source | Content |
|--------|--------|---------|
| `KIRO_AUTH_TOKEN` | `sqlite3 ~/Library/Application\ Support/kiro-cli/data.sqlite3 "SELECT value FROM auth_kv WHERE key='kirocli:odic:token';"` | JSON with access_token, refresh_token, expires_at, region, scopes |
| `KIRO_DEVICE_REG` | `sqlite3 ~/Library/Application\ Support/kiro-cli/data.sqlite3 "SELECT value FROM auth_kv WHERE key='kirocli:odic:device-registration';"` | JSON with client_id, client_secret, client_secret_expires_at, region, scopes |

**Token refresh:** The access_token expires (currently hourly), but the refresh_token is long-lived. `kiro-cli-chat` auto-refreshes using the refresh_token + device-registration client credentials. So as long as the refresh_token and device-registration are valid, CI auth will keep working.

**Device registration expiry:** The `client_secret_expires_at` field controls when the device registration expires. When it does, re-run `kiro-cli-chat login --license free --use-device-flow` and update both secrets.
