## ISSUE 2: `parseSummaryText` retry logic silently swallows the original parse error on retry success

**Location:** `cmd/entire/cli/summarize/claude.go`, `parseSummaryText` function

**Severity:** MEDIUM

**Issue Description:** The `parseSummaryText` function implements a brace-matching retry strategy when the initial JSON parse fails. When the retry succeeds (matching from `{` to last `}`), the function returns success with zero indication that the original parse failed and a fallback was used. The original error is silently discarded.

```go
if retryErr := json.Unmarshal([]byte(candidate), &amp;summary); retryErr == nil {
    return &amp;summary, nil  // Original parse error is lost
}
```

This means: (a) there is no logging that a recovery was needed, so the caller cannot distinguish a clean parse from a dirty one; (b) the pattern could mask cases where the brace-matching accidentally extracts a valid but wrong JSON object from surrounding text (e.g., a code block in the LLM response that happens to contain a valid JSON object that is NOT the intended summary).

**Hidden Errors:** If the LLM returns text like `Here is your summary: {...valid JSON...} and some trailing text`, the first parse fails, the retry strips the surrounding text and succeeds. This works, but there is no log entry to help diagnose cases where the wrong JSON object was extracted.

**User Impact:** Low immediate impact (the retry is genuinely useful), but it creates a debugging blind spot. When users report "my summary has wrong content", there will be no evidence in logs that a recovery path was taken.

**Recommendation:** Add a `logging.Debug` or `logging.Info` call when the retry path succeeds, logging both the original error and the fact that brace extraction was used. This also applies to all providers using `parseSummaryText` through the shared `TextGeneratorAdapter`.
