## Error Handling Audit: PR #877 - Compact Transcript Offset Tracking

### Overview

This PR introduces `CompactTranscriptStart` tracking for v2 checkpoint metadata. It adds offset computation for compact (transcript.jsonl) transcripts that parallels the existing `CheckpointTranscriptStart` for full (full.jsonl) transcripts. The core risk is that these two offset tracking systems can silently diverge, producing corrupted checkpoint metadata that is extremely difficult to debug after the fact.

---

### Issue 1: `computeCompactOffset` in `cmd/entire/cli/migrate.go` -- Silent fail-open to 0 with no logging

**Location:** `/Users/ninawork/entire/devenv/cli/cmd/entire/cli/migrate.go`, lines 454-476

**Severity:** HIGH

**Issue Description:**
This function returns 0 on five distinct failure paths, none of which produce any log output:
1. `startLine == 0` (legitimate first checkpoint -- this is correct)
2. `len(fullTranscript) == 0` (empty transcript -- could indicate data corruption during migration)
3. `m.Agent == ""` (missing agent -- could indicate incomplete v1 metadata)
4. `compact.Compact` returns an error or empty output (compaction engine failure)
5. `offset &lt; 0` (mathematical impossibility indicating a bug in the compaction logic)

The function's sibling `computeCompactTranscriptStart` in the condensation file logs a warning on the `compact.Compact` failure path and on the negative offset path. This function does neither.

**Hidden Errors:**
- Data corruption in v1 checkpoint transcripts that produce empty bytes
- A compaction engine bug that produces more scoped lines than full lines (negative offset)
- Metadata corruption where `Agent` field was lost

**User Impact:**
During migration (`entire migrate v2`), a non-zero offset checkpoint will silently receive `CompactTranscriptStart = 0` in its v2 metadata. When a consumer later reads this checkpoint and uses the offset to slice the compact transcript, they will read from the beginning instead of the correct position, producing duplicate or incorrect data. The user will see incorrect checkpoint content with no indication that migration produced an incorrect offset. This is especially insidious because migration is a one-time operation -- the bad offset is baked into permanent storage on `entire/checkpoints/v1`.

**Recommendation:**
Add `logging.Warn` calls on the non-trivial failure paths (compact error, empty output, negative offset). The `startLine == 0` early return is correct and needs no warning. The `m.Agent == ""` case is already warned in `tryCompactTranscript` upstream, so it could arguably be skipped here, but the compact failure and negative offset paths have no other warning coverage.

**Example fix:**
```go
func computeCompactOffset(fullTranscript, scopedCompact []byte, m checkpoint.CommittedMetadata) int {
    startLine := m.GetTranscriptStart()
    if startLine == 0 || len(fullTranscript) == 0 || m.Agent == "" {
        return 0
    }

    fullCompacted, err := compact.Compact(fullTranscript, compact.MetadataFields{
        Agent:      string(m.Agent),
        CLIVersion: versioninfo.Version,
        StartLine:  0,
    })
    if err != nil || len(fullCompacted) == 0 {
        logging.Warn(ctx, "failed to compute compact offset during migration, using 0",
            slog.String("checkpoint_id", string(m.CheckpointID)),
            slog.String("error", fmt.Sprintf("%v", err)),
        )
        return 0
    }

    fullLines := bytes.Count(fullCompacted, []byte{'\n'})
    scopedLines := bytes.Count(scopedCompact, []byte{'\n'})
    offset := fullLines - scopedLines
    if offset &lt; 0 {
        logging.Warn(ctx, "compact offset computation produced negative value, using 0",
            slog.String("checkpoint_id", string(m.CheckpointID)),
            slog.Int("full_lines", fullLines),
            slog.Int("scoped_lines", scopedLines),
        )
        return 0
    }
    return offset
}
```

Note: this function currently does not accept `ctx context.Context` as a parameter. Adding it would be required to enable logging, which is a small signature change. The caller `migrateOneCheckpoint` already has `ctx` available.

### Issue 3: `buildCompactTranscript` -- Redaction failure sets `redacted = nil`, then `compactTranscriptForV2` is called with nil transcript

**Location:** `/Users/ninawork/entire/devenv/cli/cmd/entire/cli/strategy/manual_commit_condensation.go`, lines 326-358

**Severity:** HIGH

**Issue Description:**
When `redact.JSONLBytes` fails (line 332), the code sets `redacted = nil` and continues. Then on lines 348-354, both `compactTranscriptForV2` calls receive `nil` as the `transcript` parameter. Looking at `compactTranscriptForV2` (line 1200), it checks `len(transcript) == 0` and returns `nil` when the transcript is nil/empty. So both `scopedCompact` and `writeOpts.CompactTranscript` will be `nil`.

Then `computeCompactTranscriptStart` is called with `nil` for both `transcript` and `scopedCompact`. Looking at line 1238, both `len(transcript) == 0` and `len(scopedCompact) == 0` trigger the early return of 0. So `writeOpts.CompactTranscriptStart` = 0.

The net effect: when redaction fails, `CompactTranscript = nil` and `CompactTranscriptStart = 0`. Then back in `CondenseSession` (line 268-271), `compactLines = 0` because `writeOpts.CompactTranscript` is nil. So `CompactTranscriptLines = 0` is returned in the result.

Then at the accumulation sites (lines 1028, 1137, 1317):
```go
state.CompactTranscriptStart += result.CompactTranscriptLines // += 0, no progress
```

This means: **if redaction fails for one checkpoint, the compact offset stops advancing, and every subsequent checkpoint in the session will have a stale/wrong `CompactTranscriptStart`**. The warning log at line 335 says "skipping transcript.jsonl on /main", which is accurate for the current checkpoint, but there is no indication that this has permanently corrupted the offset tracking for all future checkpoints in this session.

**Hidden Errors:**
- Any `redact.JSONLBytes` failure (malformed JSON, unexpected structure) poisons the entire session's compact offset chain
- The user sees a single warning about one checkpoint but has no idea that all subsequent checkpoints are also affected

**User Impact:**
A transient redaction failure (e.g., one malformed JSON line in the transcript) permanently corrupts the compact offset for the rest of the session. All subsequent checkpoints will have `CompactTranscriptStart` pointing to the wrong position. When a consumer reads these checkpoints and tries to slice the compact transcript, they will get wrong content.

**Recommendation:**
This is an architectural issue with the accumulation pattern. When `CompactTranscriptLines` is 0 due to a failure (not because there genuinely are 0 lines), the accumulation should be handled differently. Options:

1. **Best option:** When redaction fails, attempt to compute what `CompactTranscriptLines` *would have been* from the un-redacted transcript. The compact offset is about line counts, not about whether the transcript was actually written to storage.

2. **Minimum fix:** Log a warning at ERROR level (not WARN) that explicitly states the session's compact offset tracking is now broken and will produce incorrect metadata for subsequent checkpoints. This at least makes the failure debuggable.

3. **Consider propagating the error** instead of swallowing it. If compact transcript generation is important enough to track offsets for, a redaction failure should perhaps prevent the v2 write rather than silently producing corrupt metadata.

### Issue 4: `buildCompactTranscript` -- If scoped compact succeeds but full compact fails (or vice versa), inconsistent state is produced

**Location:** `/Users/ninawork/entire/devenv/cli/cmd/entire/cli/strategy/manual_commit_condensation.go`, lines 347-354

**Severity:** MEDIUM

**Issue Description:**
Lines 348-353 make two independent calls to `compactTranscriptForV2`:
```go
scopedCompact := compactTranscriptForV2(compactCtx, ag, redacted, state.CheckpointTranscriptStart)
writeOpts.CompactTranscript = compactTranscriptForV2(compactCtx, ag, redacted, 0)
```

These call `compact.Compact` with different `StartLine` values. If one succeeds and the other fails (returns nil), you get inconsistent state:

- **Scoped succeeds, full fails:** `scopedCompact` is non-nil but `writeOpts.CompactTranscript` is nil. Then `computeCompactTranscriptStart` gets a valid `scopedCompact` and computes an offset. But `writeOpts.CompactTranscript` is nil, so `compactLines = 0` in the result (line 268-271). The offset was computed but the transcript was not written. The `CompactTranscriptStart` in metadata is non-zero, but there is no transcript.jsonl to slice.

- **Full succeeds, scoped fails:** `scopedCompact` is nil, `writeOpts.CompactTranscript` is non-nil. `computeCompactTranscriptStart` gets `len(scopedCompact) == 0`, returns 0. The full compact transcript is written with `CompactTranscriptStart = 0`. Meanwhile `compactLines = fullLines - 0 = fullLines`, which would be the entire cumulative line count, not just the new lines. This would cause `CompactTranscriptLines` to be inflated, and the next checkpoint's `CompactTranscriptStart` would jump forward incorrectly.

**Hidden Errors:**
- `compact.Compact` could fail for `StartLine=N` but succeed for `StartLine=0` (e.g., truncation produces invalid JSONL for some agent formats)
- Or vice versa: `StartLine=0` might hit an error in a later portion of the transcript that `StartLine=N` skips

**User Impact:**
Inconsistent compact offset metadata. In the "full succeeds, scoped fails" case, the inflated `CompactTranscriptLines` causes every subsequent checkpoint to have an offset that is too large, pointing past the end of the actual compact content.

**Recommendation:**
Add a consistency check: if either compact call returns nil, treat both as nil. This prevents partial/inconsistent state.

**Example fix:**
```go
scopedCompact := compactTranscriptForV2(compactCtx, ag, redacted, state.CheckpointTranscriptStart)
fullCompact := compactTranscriptForV2(compactCtx, ag, redacted, 0)

// Both must succeed for consistent offset tracking. If either fails,
// skip compact transcript entirely for this checkpoint.
if scopedCompact != nil &amp;&amp; fullCompact != nil {
    writeOpts.CompactTranscript = fullCompact
    writeOpts.CompactTranscriptStart = computeCompactTranscriptStart(compactCtx, ag, state, redacted, scopedCompact)
} else if scopedCompact != nil || fullCompact != nil {
    logging.Warn(ctx, "partial compact transcript success, skipping to avoid inconsistent offsets",
        slog.String("session_id", state.SessionID),
        slog.Bool("scoped_ok", scopedCompact != nil),
        slog.Bool("full_ok", fullCompact != nil),
    )
}
```

### Issue 5: State accumulation `CompactTranscriptStart += CompactTranscriptLines` appears in 3 places with no validation

**Location:**
- `/Users/ninawork/entire/devenv/cli/cmd/entire/cli/strategy/manual_commit_condensation.go`, line 1028
- `/Users/ninawork/entire/devenv/cli/cmd/entire/cli/strategy/manual_commit_condensation.go`, line 1137
- `/Users/ninawork/entire/devenv/cli/cmd/entire/cli/strategy/manual_commit_hooks.go`, line 1317

**Severity:** HIGH

**Issue Description:**
The pattern `state.CompactTranscriptStart += result.CompactTranscriptLines` appears in 3 separate locations. This is the same additive accumulation pattern used for `CheckpointTranscriptStart`, but with a critical difference: `CheckpointTranscriptStart` is assigned (`=`), not accumulated (`+=`):

```go
state.CheckpointTranscriptStart = result.TotalTranscriptLines   // absolute assignment
state.CompactTranscriptStart += result.CompactTranscriptLines    // relative accumulation
```

This asymmetry is dangerous. `CheckpointTranscriptStart` is self-correcting -- if one condensation produces the wrong total, the next condensation's `TotalTranscriptLines` will still be correct because it counts the full transcript. But `CompactTranscriptStart` is an accumulator -- if `CompactTranscriptLines` is 0 due to a silent failure (Issues 3 and 4 above), the offset stops advancing permanently and never recovers.

Additionally, there is no validation that `CompactTranscriptLines` is non-negative or reasonable. If the `compactLines` calculation at lines 268-271 produces a negative value (possible if `writeOpts.CompactTranscriptStart` is somehow larger than the full compact line count), then `CompactTranscriptStart` would decrease, which makes no sense for a monotonically increasing offset.

**Hidden Errors:**
- Any silent failure in `buildCompactTranscript` that sets `CompactTranscriptLines = 0` permanently breaks the accumulation chain
- `compactLines` could be negative if `writeOpts.CompactTranscriptStart` exceeds `fullLines` (no guard)

**User Impact:**
Once the accumulation goes wrong, every subsequent checkpoint in the session has an incorrect compact offset. The full-transcript offset (`CheckpointTranscriptStart`) continues to be correct, creating a confusing situation where v1 metadata is right but v2 metadata is wrong.

**Recommendation:**
1. Add a guard to ensure `compactLines` at lines 268-271 is never negative:
```go
compactLines := 0
if writeOpts.CompactTranscript != nil {
    fullLines := countCompactLines(writeOpts.CompactTranscript)
    compactLines = fullLines - writeOpts.CompactTranscriptStart
    if compactLines &lt; 0 {
        logging.Warn(ctx, "compact lines calculation produced negative value",
            slog.String("session_id", state.SessionID),
            slog.Int("full_lines", fullLines),
            slog.Int("compact_start", writeOpts.CompactTranscriptStart),
        )
        compactLines = 0
    }
}
```

2. Consider whether the accumulation pattern is the right design. An alternative is to compute `CompactTranscriptStart` from the total compact line count (like `CheckpointTranscriptStart` does for the full transcript), making it self-correcting rather than dependent on perfect accumulation.
