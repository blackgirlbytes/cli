## Issues to Fix

### 1. `implementer.md` Step 3 references nonexistent `config.go`

**File:** `implementer.md:47`
**Problem:** Says "Add the agent to the config map in `cmd/entire/cli/agent/config.go`" — this file doesn't exist. Agent wiring uses blank imports in `cmd/entire/cli/hooks_cmd.go`.
**Fix:** Replace with: "Ensure the blank import `_ "github.com/entireio/cli/cmd/entire/cli/agent/$AGENT_SLUG"` exists in `cmd/entire/cli/hooks_cmd.go`"

### 2. `researcher.md` Phase 4 asks for info the researcher can't produce

**File:** `researcher.md:67`
**Problem:** Phase 4 says "Field coverage: which `Event` struct fields can be populated per event" — but the researcher was told NOT to read `event.go` where `Event` struct fields are defined. The researcher can't assess field coverage without knowing the struct.
**Fix:** Remove the "Field coverage" bullet from Phase 4. The implementer handles field mapping when reading `event.go`.

### 3. One-pager template missing "Static Checks" section

**File:** `researcher.md:81-122`
**Problem:** Phase 2 runs 7 static checks (binary, help, version, hook keywords, session keywords, config dir, docs). These results aren't captured in the one-pager template. The verdict (COMPATIBLE/PARTIAL/INCOMPATIBLE) depends on these checks, but there's no place to record the detailed results.
**Fix:** Add a `## Static Checks` section to the template between `## Verdict` and `## Binary`:
```markdown
## Static Checks
| Check | Result | Notes |
|-------|--------|-------|
| Binary present | PASS/FAIL | path |
| Help available | PASS/FAIL | |
| ... | ... | ... |
```

### 4. `implementer.md` Step 13 partially redundant with Step 3

**File:** `implementer.md:227-231`
**Problem:** Step 13 says "Register hook commands: Search `cmd/entire/cli/` for where hook subcommands are registered and add the new agent" — but Step 3 already says to wire up blank imports in `hooks_cmd.go`. Step 13 also says "Verify registration: The `init()` function..." which Step 3 also covers.
**Fix:** Simplify Step 13 to just verification: "Verify registration by running `mise run test:ci`. The `init()` in `${AGENT_SLUG}.go` and blank import in `hooks_cmd.go` (from Step 3) should be sufficient."

### 5. `test-writer.md` Step 1 reads 8 files — no priority guidance

**File:** `test-writer.md:12-23`
**Problem:** Step 1 lists 8 infrastructure files to read. This is a lot of context to load. The most critical files for writing a new agent runner are `agent.go` (interface) and one existing agent (e.g., `claude.go`), not all 8.
**Fix:** Add a note: "**Most critical:** Focus on items 3 (`agent.go` — the interface you must implement) and read one existing agent implementation (e.g., `e2e/agents/claude.go`) as a reference. Skim the rest for context."

### 6. One-pager template doesn't list valid EventType values

**File:** `researcher.md:95-99`
**Problem:** The hook mapping table has an "Entire EventType" column, but the researcher needs to know the valid values. They learned them from `agent-guide.md` in Phase 1, but by Phase 5 they need to recall them. A reference list would prevent incorrect mappings.
**Fix:** Add a comment after the table: "Valid Entire EventTypes: `SessionStart`, `TurnStart`, `TurnEnd`, `Compaction`, `SessionEnd`, `SubagentStart`, `SubagentEnd`"

### 7. `SKILL.md` doesn't mention AGENT.md lifecycle

**File:** `SKILL.md:36-62`
**Problem:** The one-pager is created by Phase 1 and consumed by Phases 2 and 3, but SKILL.md doesn't explicitly state that Phases 2/3 may update it. The implementer.md has the standing instruction, but the orchestration doc should also note this.
**Fix:** Add a brief note after Phase 3: "**Note:** `AGENT.md` is a living document — Phases 2 and 3 update it when they discover new information during testing."
