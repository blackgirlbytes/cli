IsLinkedWorktree currently returns true for any repo where .git is a file. That also matches git submodules (and other gitfile-based setups), which would cause MainRepoRoot/IsInsideWorktree to treat submodules as linked worktrees and potentially resolve paths to the superproject instead of the submodule repo. Consider reading the .git gitfile and only returning true when gitdir: points into a worktree admin dir (e.g. contains /.git/worktrees/ or /.bare/worktrees/), or reuse GetWorktreeID and treat “no worktrees marker” as not a linked worktree; update TestIsLinkedWorktree accordingly.

MainRepoRoot derives the main repo by searching for "/.git/" in the gitdir value. This will fail for bare-repo worktree layouts (which you already handle in GetWorktreeID via ".bare/worktrees/") and can also fail if the gitfile uses a relative path or OS-specific separators. Suggest normalizing with filepath.ToSlash, resolving relative gitdir against worktreeRoot, and supporting both /.git/worktrees/ and /.bare/worktrees/ markers when computing the main repo root.

The git worktree add invocation appears to have arguments in the wrong order: -b <branch> is an option and (per git worktree add syntax) should come before the <path> positional arg. As written, Git may interpret -b as the commit-ish argument and fail on some versions; consider using git worktree add -b test-branch <worktreeDir> (or --checkout etc as needed).
