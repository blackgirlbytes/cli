## Type: `EventType` (modified) -- `FileEdit` constant

**File:** `/Users/alex/workspace/cli/.worktrees/3/cmd/entire/cli/agent/event.go`

### Invariants Identified
- `EventType` is a closed set of lifecycle events (`iota + 1` through `FileEdit`)
- Zero value is intentionally invalid (iota starts at 1)
- Every `EventType` must have a corresponding `String()` case
- Every `EventType` must have a corresponding dispatcher case in `DispatchLifecycleEvent`

### Ratings
- **Encapsulation**: 6/10
  The type is `int`-based, meaning any int can be cast to `EventType`. This is standard Go practice for iota enums and is acceptable given that the `default` arm in `DispatchLifecycleEvent` returns an error for unknown types. The real enforcement boundary is the dispatcher, not the type itself.

- **Invariant Expression**: 7/10
  The new `FileEdit` constant is appended at the end of the iota sequence, preserving backward-compatible wire values for all existing constants. The `String()` method and dispatcher both handle it. The comment on the constant clearly explains its purpose and the framework's expected behavior (appending to tracking file).

- **Invariant Usefulness**: 8/10
  `FileEdit` fills a genuine gap: before this PR, file tracking required transcript parsing at commit time, which is expensive and error-prone. Making it an explicit lifecycle event allows real-time incremental tracking. The event type clearly distinguishes "file was modified" from all other lifecycle phases.

- **Invariant Enforcement**: 6/10
  No enforcement that `FileEdit` events must have a non-empty `FilePath`. The dispatcher in `handleLifecycleFileEdit` handles this gracefully (returns nil), but the type itself allows construction of `FileEdit` events with empty `FilePath`. This is a pragmatic tradeoff -- see Concerns below.

### Strengths
- Clean extension of the existing enum pattern
- iota ordering is backward-compatible (new constant appended at the end)
- String() method and dispatcher are both updated in lockstep

### Concerns
- The `Event` struct is a flat "god struct" with fields that are only relevant for specific event types (`FilePath` for `FileEdit`, `ToolUseID` for subagent events, `Prompt` for `TurnStart`, etc.). This is a pre-existing design issue that this PR does not worsen significantly by adding one more field.
- There is no compile-time enforcement that a `FileEdit` event has a `FilePath`. A discriminated union or sealed interface would express this more strongly, but that would be a large architectural change inconsistent with the codebase's established patterns.

### Recommended Improvements
None for this PR. The flat-struct approach is a conscious tradeoff in this codebase, and adding one more field does not cross a complexity threshold that would justify refactoring the Event type.

**File:** `/Users/alex/workspace/cli/.worktrees/3/cmd/entire/cli/session/state.go`, lines 412-502

1. Session ID must pass `validation.ValidateSessionID` (prevents path traversal)
2. File paths must not contain `\n` or `\r` (prevents line injection in the append-only format)
3. The `.files` tracking file uses one-path-per-line format with newline delimiters
4. `ReadFilesTouched` deduplicates and sorts
5. `ClearFilesTouched` is idempotent (no error on non-existent file)
6. `Clear()` already uses a glob (`sessionID+".*"`) to remove all session files, so `.files` is automatically cleaned up

  All file path manipulation is internal. The public API is `AppendFileTouched(ctx, sessionID, filePath)` -- callers don't know about the `.files` file format. The `filesTouchedPath` helper is private. The design is clean.

- **Invariant Expression**: 8/10

- **Invariant Usefulness**: 9/10
  These methods solve a critical performance problem: the previous approach required parsing the full transcript at commit time to discover which files were modified. The new append-only tracking file makes this O(1) per tool invocation, with read being O(n) in files touched (which is always small). The design is intentionally lightweight -- no JSON parsing, no file locking, just `O_APPEND` writes.

- **Invariant Enforcement**: 8/10
  - Session ID validated on every operation (Append, Read, Clear)
  - Newline injection prevented on write
  - Directory created with restrictive permissions (0o750)
  - File created with restrictive permissions (0o600)
  - Idempotent clear (no error on non-existent)
  - Existing `Clear()` method already cleans up `.files` via the `sessionID+".*"` glob pattern

### Strengths
- The append-only write / deduplicate-on-read pattern is a smart design for this use case. It avoids any need for file locking even with concurrent tool invocations within the same session.
- `O_APPEND` is atomic on POSIX for writes smaller than `PIPE_BUF` (4096 bytes), so concurrent appends of file paths will not interleave.

### Concerns
1. **No file locking for concurrent sessions.** Two concurrent sessions with the same session ID could write to the same `.files` file. None for this PR. The append-only pattern is the right tradeoff for a hot path (called on every file edit). The unbounded growth concern is mitigated by the clearing at commit time.

# Error Handling Audit: `post-file-edit-gemini` PR

## Summary

This PR introduces a `FileEdit` lifecycle event to track files modified by agents (both Claude Code and Gemini CLI) via per-session `.files` tracking files. It also modifies `resolveFilesTouched` to merge state and tracking file data, and adds `clearFilesTracking` calls during condensation and carry-forward. Overall, the error handling quality is moderate to good -- most errors are logged and the design intent of "never block the agent" is clear. However, there are several issues ranging from medium to high severity.

---

## Issue 1: `handleLifecycleFileEdit` silently swallows all errors -- returns nil unconditionally

**Location:** `/Users/alex/workspace/cli/.worktrees/3/cmd/entire/cli/lifecycle.go`, lines 179-219

**Severity:** HIGH

**Issue Description:** The function comment explicitly states "Returns nil unconditionally; errors are logged but not propagated to avoid blocking the agent." While the *intent* is defensible (a file-tracking failure should not block the agent), every error path returns `nil` after only a `Warn`-level log. This means callers (specifically `DispatchLifecycleEvent`) receive no indication that anything went wrong. The design choice to never propagate errors from this handler means:

1. If `paths.WorktreeRoot` consistently fails (e.g., corrupted `.git`), every single file edit will silently fail tracking, and the user will discover at commit time that none of their session's files were tracked -- with no explanation.
2. If `session.NewStateStore` fails (e.g., permissions issue on `.git/entire-sessions/`), the same silent failure pattern accumulates indefinitely.

**User Impact:** Users will see stale or empty `FilesTouched` data at commit time with no explanation of why file tracking stopped working. The `resolveFilesTouched` function will fall back to transcript extraction (which is slower and less reliable), and the user will never know the tracking mechanism broke.

**Recommendation:** This is a legitimate design decision (don't block the agent), but it should be documented more clearly in the function, and the logging should be at `Error` level for repeated failures, not just `Warn`. At minimum, consider returning the error wrapped in a non-fatal marker so callers can log appropriately. The current approach of `Warn` logging is adequate for individual failures but provides no mechanism to escalate when failures are persistent.

	store, storeErr := s.getStateStore(ctx)

		return  // <-- SILENT RETURN, NO LOGGING

	...
