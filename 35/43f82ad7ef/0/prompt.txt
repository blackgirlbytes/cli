Findings:

1. `entire stats` silently truncates its dataset at 500 records, so heavy users will get undercounted repo totals, commit lists, and any checkpoint-derived metrics with no indication that the view is partial. The command hard-codes `statsLimit = 500` and issues exactly one request per endpoint in [stats_cmd.go](/Users/soph/Work/entire/devenv/cli_experiments/cmd/entire/cli/stats_cmd.go:16) and [stats_cmd.go](/Users/soph/Work/entire/devenv/cli_experiments/cmd/entire/cli/stats_cmd.go:95). If the API paginates, this needs pagination; if it intentionally caps results, the UI should say it is showing the latest 500.

2. Repository ordering is nondeterministic when two repos have the same checkpoint count. `computeRepoContributions` builds from a Go map and sorts only by `Total`, so ties inherit randomized map iteration order, which means the “top repos” chart can jitter between runs for identical data. See [stats_cmd.go](/Users/soph/Work/entire/devenv/cli_experiments/cmd/entire/cli/stats_cmd.go:225). Add a stable tie-breaker such as repo name.

Assumptions: I’m assuming the stats endpoints can return more than 500 items and that stable output order matters for a CLI summary view.
