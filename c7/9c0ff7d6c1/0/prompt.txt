### 1. Architecture Overview

The branch cleanly separates a reusable OAuth library (`auth/`) from an entire-specific shim (`cmd/entire/cli/auth/`). Library has 5 subpackages plus `internal/oauthhttp`; the shim adds provider tables, env-var reads, keyring service name, legacy bare-string fallback, and singleton wiring. **Library purity (good).** `grep` for env-var reads under `auth/` returns nothing. `auth/doc.go:13-16` and `auth/README.md:5,98-102` explicitly forbid globals/env vars/implicit URLs, and the code matches the stated contract. `tokenmanager.Config` (`auth/tokenmanager/tokenmanager.go:55-97`) takes every wire-affecting value as a field. `sts.Client` (`auth/sts/sts.go:76-80`) and `deviceflow.Client` are field-bag structs — no provider table inside the library.

# Security Review: `alex/cli-auth-consolidation` auth library

Scope: `auth/{deviceflow,sts,tokens,tokenstore,tokenmanager,internal/oauthhttp}`, `cmd/entire/cli/auth/`, `cmd/entire/cli/api/auth_tokens.go`, `cmd/entire/cli/{api_client,login,logout}.go`, `cmd/entire/cli/dispatch/`.

Overall posture: solid. The cache key correctly binds `(core, resource, audience, requested_token_type, scope)`; `coreTokenAudienceIncludes` is the only consumer of `tokens.ParseClaims` and is used only for routing (matches README); `DeleteCoreToken` ordering matches spec (keyring first, cache only on success) and is pinned by `TestDeleteCoreToken_PreservesCacheOnStoreFailure`; tokens never appear in logs or URLs; no `Bearer ` mangling. No critical or high findings.

## Findings

### Medium

1. **No core-token expiry check before reuse** — `auth/tokenmanager/tokenmanager.go:229-234` and `:336-363`. The same-host shortcut, the JWT-aud shortcut, and the STS exchange all use the stored core token verbatim with no `tokens.Claims.ExpiresAt` check. A long-expired core token will be sent on every call and rejected with 401 by the resource (or, worse, returned by STS as an opaque error and surfaced as a confusing `token exchange: status 400: invalid_grant`). On a server that accepts an expired-but-undetected token (clock skew), it could even be exchanged for a fresh resource token. The core token's `exp` is already accessible via `tokens.ParseClaims`; either preflight-check it or surface a `re-login required` error rather than a generic STS failure. Not a confidentiality issue, but a real correctness/availability cliff for users who leave the CLI logged in for weeks.

2. **`SaveCoreToken` does not clear the exchange cache** — `auth/tokenmanager/tokenmanager.go:140-142`. `DeleteCoreToken` clears it; `SaveCoreToken` does not. In practice the cache key includes `CoreToken`, so a new core can't return a stale exchanged token, but the old entries linger until process exit. If a future refactor were to drop `CoreToken` from the cache key (e.g., to share exchanges across re-logins for the same user), this becomes exploitable: a re-login under a different user could hand back the prior user's exchanged tokens. Either clear the cache on save, or add a comment-and-test pinning the invariant that `CoreToken` is the load-bearing isolator.

3. **STS response `issued_token_type` is decoded but never validated against the request** — `auth/sts/sts.go:128`. RFC 8693 §2.2.1 requires a server response to include `issued_token_type`; the library accepts whatever the server returns, then the manager caches the result keyed by `RequestedTokenType` regardless. If a misconfigured server downgrades (e.g., issues an opaque access token when JWT was requested) the CLI silently uses the wrong shape. Low likelihood; spec-required validation.

### Low

4. **String-equality `Resource` comparison without normalisation** — `auth/tokenmanager/tokenmanager.go:229,232` (`m.cfg.Issuer == req.Resource`, `slices.Contains(claims.Audience, target)`). Trailing slash, case in scheme/host, default-port differences cause the same-host and aud-shortcuts to miss and force an exchange. Not a confidentiality issue but predictable footgun: a user rotating `ENTIRE_AUTH_BASE_URL=https://entire.io/` (trailing slash) will burn an STS round-trip every call. Normalise both sides through `url.Parse` + canonical form, or document strict `==` matching.

5. **Auth-tokens path picker reads the env var directly** — `cmd/entire/cli/api/auth_tokens.go:32-42`. `authTokensProviderVersionEnvVar` duplicates `auth.ProviderVersionEnvVar`; the comment justifies it as avoiding an import cycle, but it means a future provider rename/typo in one constant won't break the other. If `ENTIRE_AUTH_PROVIDER_VERSION` ever drifts (e.g., a `v3` only the auth package knows about), `ListTokens`/`RevokeToken` will route to the v1 path while login goes to v3. Low risk today, but worth a single-source-of-truth helper in a leaf package both can import.

6. **`readAPIErrorResponse` (deviceflow) dumps up to 1MB of HTML on non-200 with HTML body** — `auth/deviceflow/deviceflow.go:248-264`. Only the success path (`ReadAndDecodeJSON`) detects HTML and surfaces `ErrNonJSONResponse`. A captive portal returning 502 with an HTML page falls through to `text := strings.TrimSpace(string(body))` and the entire HTML appears in the error message. UX issue, not security, but consistency would be good — share the HTML detector.

7. **`StartDeviceAuth` uses `DisallowUnknownFields` (strict=true); `PollDeviceAuth` does not** — `auth/deviceflow/deviceflow.go:130,177`. Asymmetric. A compromised/buggy AS that adds a field to `Start` fails the response, but the same field on `Poll` is silently ignored. Not exploitable today; pin both to strict for defence-in-depth, or document why poll is permissive.

8. **Login retries on transient errors *include* `ErrNonJSONResponse`** — `cmd/entire/cli/login.go:118-130` reaches the transient branch if `PollDeviceAuth` returns any error that doesn't pass `oauthErrorParts`. An HTML-returning captive portal causes 5 polls before giving up (~5–25s wasted, plus repeated bursts of error to the user). Minor.

### Nit

9. **`auth/sts/sts.go:200`** — the body read in `readAPIError` swallows the read error with `//nolint:errcheck`. Best-effort is fine; document so future readers don't assume the body is complete.

10. **`auth/tokenstore/keyring.go:104`** — encoded TokenSet JSON includes empty `expires_at` only via `omitempty` on the wire struct; `t.Scope` and `t.TokenType` likewise. Looks fine; nothing to fix.

# Code Review — `alex/cli-auth-consolidation`

## High

- **`SetManagerForTest` racy package var** — `cmd/entire/cli/auth/exchange.go:30,38`. `managerForTest` is a plain package var accessed without a mutex; the comment at line 30 calls out "tests use SetManagerForTest" but every test that touches it (`exchange_test.go:60`, `provider_test.go`) must remain non-parallel forever or the race detector will fire. The current test in `exchange_test.go:44` correctly notes "Not parallel", but as written the foot-gun is invisible to future contributors. Either guard with a `sync.Mutex`/`atomic.Pointer`, or have `SetManagerForTest` panic if called from a test that has already opted into `t.Parallel()` (no clean way), or document in the function godoc that callers must not run in parallel. The doc-only fix is fine, but this is one wrong `t.Parallel()` away from a flaky CI.

- **`defaultManager` singleton vs env-driven config** — `cmd/entire/cli/auth/exchange.go:48,52`. `sync.Once` permanently pins `Issuer/STSPath/clientID` to whatever the first caller saw. Any non-test code path that triggers `TokenForResource` during package init or before `t.Setenv("ENTIRE_API_BASE_URL", …)` runs in a test will cement the wrong issuer. The comment at exchange.go:46 acknowledges this but production has the same hazard during partial process upgrades (`exec.Command` chains, etc.). At minimum, log/panic if the second `defaultManager()` call observes a different `api.AuthBaseURL()` than the cached manager's `Issuer()`.

- **Library `Issuer == Resource` comparison is byte-exact** — `auth/tokenmanager/tokenmanager.go:229`. If a third-party caller passes `https://entire.io` for `Issuer` and `https://entire.io/` for `Resource`, the same-host shortcut misses and STS fires unnecessarily — or worse, fails because `Config.STSPath` is empty (single-host expectation), surfacing `ErrNoSTSPath` instead of the core token. Same root cause as above: `cacheKey.Resource` stores the caller-supplied string, so `https://api.entire.io` and `https://api.entire.io/` cache as two entries. Not a correctness bug today but doubles the exchange count for sloppy callers.

## Medium

- **`tokenstore/keyring.go` decodes lenient JSON without trip-wire** — `auth/tokenstore/keyring.go:111-131`. Any well-formed JSON object (e.g. an unrelated CLI's blob the user happens to have keyed against the same `(service, profile)`) decodes to `keyringTokenSet{}` with a zero AccessToken, so it returns `tokens.TokenSet{}` with no error. The manager then sees a stored entry with empty access token and returns `ErrNotLoggedIn` rather than triggering the bare-string fallback. - **`auth/tokens/tokens.go:121` `decodeAudience` masks underlying error** — when `aud` is a JSON object/number, both `Unmarshal` calls fail and the returned error reads `"decode JWT aud claim: not a string or array"` with no source-error context. - **`auth/sts/sts.go:117` swallowed transport error** — `httpClient.Do` failure returns `fmt.Errorf("token exchange: %w", err)`, but the caller (`tokenmanager.runExchange`) further wraps via the calling shim. `cmd/entire/cli/auth/exchange.go:79` already returns the lib error verbatim, so a single 30s outage propagates as `"resolve API token: token exchange: Post …: dial tcp: i/o timeout"`. If keyring lookup fails with anything other than `ErrNotFound`/`ErrMalformed`, the user sees `"resolve API token: load core token: get token from keyring: &lt;error&gt;"`. That's correct error propagation but no path-to-recover guidance ("run keyring unlock", "set ENTIRE_AUTH_BASE_URL", etc.). Minor UX fit-and-finish.

The 1 MB cap protects against huge bodies, but a slow-loris HTML response that drips bytes within `MaxResponseBytes` will block the whole poll loop until the read completes. The HTTP client has no per-request `Timeout`. Set a sensible default `c.HTTP.Timeout` in `deviceflow.Client` / `sts.Client` constructors, or use a `context.WithTimeout` inside the Exchange/Poll method bodies.

- **`exchange.go:35` interface accepts only `Helper()`** — fine for tests, but `t.Cleanup` would be more idiomatic and would let `SetManagerForTest` register its own cleanup so callers can't forget the `defer cleanup()`.
