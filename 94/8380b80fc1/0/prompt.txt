Medium Severity

When a user runs entire disable (writes enabled: false to settings.local.json) and then entire enable --project, runEnable writes enabled: true to settings.json but doesn't clear the enabled: false in settings.local.json. Because settings.Load merges both files with local overriding project, the effective state remains disabled. The user sees "Entire is now enabled." but IsEnabled() still returns false.

runSetupFlow always calls runEnableInteractive with an empty EnableOptions{}. As a result, flags provided to entire enable / entire configure on first-time setup (e.g. --local/--project, --skip-push-sessions, --telemetry=false, --absolute-git-hook-path, etc.) are ignored when the repo is fresh. Consider passing the caller’s EnableOptions into runSetupFlow (e.g. runSetupFlow(ctx, w, opts)) and forwarding it to runEnableInteractive so initial setup honors the CLI flags.

---

In entire configure --agent ... mode, the command calls agent.Get(...) without first running external.DiscoverAndRegister(ctx). This means external agent plugins (entire-agent-* binaries) won’t be found even when external_agents is enabled, and the command will incorrectly report “Unknown agent”. Recommend calling external.DiscoverAndRegister(ctx) before checking/using --agent (and before listing agents).
