  - In fact, the prompt explicitly allows a singleton exception for strong
    review-derived rules: cmd/entire/cli/memoryloop/generator.go:316

  So your read is correct: a lot of generated memories can be plausible
  but still too episodic to be worth injecting later.

  The main gap is architectural:

  - improve.AnalyzePatterns does build repeated signals for some
    categories.
  - But memoryloop.Generate still asks the LLM to synthesize records from
    the whole analysis/session bundle, then only applies weak/generic/
    dedupe filtering afterward.
  - That means “stable” is mostly model judgment right now, not enforced
    policy.

  If you want to tighten it, the strongest fixes would be:

  1. Require repeated evidence for most generated memories.
  2. Keep singleton exceptions only for explicit classes like strong org/
     review rules.
  3. Down-rank or reject records whose source_session_ids length is 1
     unless the kind is allowlisted.
  4. Show evidence count in the TUI/CLI so weak memories are obvious
     before promotion.

codex findings 
• Findings

  1. MEMORY_QUALITY_ANALYSIS.md:78 The recommended fix assumes we can
     reliably map a generated memory back to an upstream signal, but the
     current data model does not preserve that provenance. PatternAnalysis
     does have Count fields on recurring signals, but generated memories
     only carry freeform title/body plus optional source_session_ids;
     there is no source_signal_type or source_signal_key to make this
     deterministic. The existing review gate works only because it
     compares against a dedicated review-rule field, not because the
     system generally knows where a generated memory came from (cmd/
     entire/cli/improve/improve.go, cmd/entire/cli/memoryloop/
     generator.go:164, cmd/entire/cli/memoryloop/generator.go:360). As
     written, this proposal understates the implementation risk and likely
     leads to fuzzy text-matching heuristics with false positives/
     negatives.
  2. MEMORY_QUALITY_ANALYSIS.md:119 The implementation sketch’s fallback,
     “if no matching signal found, allow,” largely nullifies the proposed
     evidence gate. The bad cases you’re trying to eliminate are precisely
     the ones that won’t map cleanly back to a repeated signal. If
     unmatched records are still allowed through, the one-off memory
     problem remains with only a narrower filter on easily matched cases.
  3. MEMORY_QUALITY_ANALYSIS.md:66 Option 4 is weaker than the doc
     suggests because some generated memories do not wait for a human
     promotion step. Personal-scope records become active immediately
     under auto activation policy (cmd/entire/cli/memoryloop/
     memoryloop.go:623). So “show evidence count in TUI before promotion”
     does not meaningfully protect the most problematic path; those
     records may inject without any TUI review at all.

  Open questions / assumptions

  - I’m assuming this document is meant to drive implementation, not just
    capture tradeoffs. If so, I’d want the recommendation rewritten around
    either:
      - adding explicit provenance to generated records, or
      - hard-gating on deterministic inputs we already have, even if that
        is a coarser rule.

  Briefly: the problem statement is right, but the recommended solution is
  not implementable as cleanly as the doc presents, and its fallback would
  leave the core failure mode in place.
