## Executive Summary

The change replaces `filepath.Walk` directory traversal with `git ls-files --others --exclude-standard` for collecting untracked files in two contexts: (1) capturing initial session state, and (2) identifying files to delete during rewind. The change is **low-risk overall** given this is a local CLI tool running inside user-owned git repos. However, there is one finding worth addressing (filenames containing newlines) and several informational observations.

**Overall Risk Rating: Low**

## Detailed Findings

### Finding 1: Filenames Containing Newlines -- Incorrect Parsing (Medium)

**File:** `/Users/soph/Work/entire/devenv/cli/cmd/entire/cli/strategy/common.go`, lines 1246-1253

**Description:**
The `gitUntrackedFiles()` function splits git output on `\n`:

```go
for _, f := range strings.Split(raw, "\n") {
    if f != "" && !isProtectedPath(f) {
        files = append(files, f)
    }
}
```

Git filenames can legally contain newline characters. When this happens, `git ls-files` without the `-z` flag will quote such filenames (wrapping them in double quotes and escaping special characters), or the newlines will cause one filename to be split into multiple entries. This leads to incorrect file paths being returned -- phantom entries that do not correspond to real files, or split entries that fail to match any actual file.

Notably, the same codebase already handles this correctly in `/Users/soph/Work/entire/devenv/cli/cmd/entire/cli/checkpoint/temporary.go` at line 1078, where `git status --porcelain -z` is used with NUL-separated output:

```go
// Use -z for NUL-separated output (handles quoted filenames with spaces/special chars)
cmd := exec.CommandContext(ctx, "git", "status", "--porcelain", "-z", "-uall")
```

**Impact:**
- A filename containing a literal newline (e.g., created by `touch $'file\nname'`) would be parsed as two separate entries, neither matching a real file.
- In the rewind context (`manual_commit_rewind.go` line 355), `filepath.Join(repoRoot, relPath)` would construct an incorrect path. The `os.Remove()` call would fail silently (file not found), so no unintended deletion occurs. However, the real file would not be deleted when it should be.
- In the `collectUntrackedFiles` context, the split filename would be stored in `UntrackedFilesAtStart`, causing incorrect preservation decisions during rewind.

**Exploitability:** Very low. Requires a user (or agent) to intentionally create a file with a newline in its name. Git discourages this. In practice, nearly no one does this.

**Recommendation:**
Use the `-z` flag to get NUL-separated output, matching the pattern already used in `checkpoint/temporary.go`:

```go
cmd := exec.CommandContext(context.Background(), "git", "ls-files", "--others", "--exclude-standard", "-z")
cmd.Dir = repoRoot
output, err := cmd.Output()
if err != nil {
    return nil, fmt.Errorf("git ls-files failed: %w", err)
}

raw := string(output)
if raw == "" {
    return nil, nil
}

var files []string
for _, f := range strings.Split(raw, "\x00") {
    if f != "" && !isProtectedPath(f) {
        files = append(files, f)
    }
}
return files, nil
```

### Finding 3: Path Traversal in `filepath.Join(repoRoot, relPath)` -- Mitigated (Low)

**File:** `/Users/soph/Work/entire/devenv/cli/cmd/entire/cli/strategy/manual_commit_rewind.go`, line 355

```go

```

**Description:**
If `relPath` from `git ls-files` output contained a path traversal component like `../../../etc/passwd`, the `filepath.Join` would resolve it to a path outside the repository, and `os.Remove` could delete an arbitrary file.

**Mitigating Factors:**
1. `git ls-files --others --exclude-standard` returns paths relative to the repository root. Git does not output paths containing `..` components in its `ls-files` output. The data source is the git index/working tree, not arbitrary user input.
2. The `isProtectedPath` check at line 1253 in `common.go` filters `.git/` and `.entire/` paths, but does not check for `..` traversal. However, since the data source is git itself, `..` would never appear.

**Q1: Is spawning `git ls-files` cheaper than `filepath.Walk` for repos with large ignored dirs?**

## 4. Risk Analysis

**Behavioral change -- gitignored files are now invisible:**

This is the most significant architectural concern. The old `filepath.Walk` implementation walked ALL files on disk (excluding only protected paths like `.git/` and `.entire/`). The new implementation uses `--exclude-standard`, which excludes files matching `.gitignore`, `.git/info/exclude`, and the global gitignore.

This is an intentional behavioral change, and the new tests validate it. But let me analyze the risk:

- **Session state (`UntrackedFilesAtStart`)**: Previously, gitignored files were captured in `UntrackedFilesAtStart`. This bloated the session state (especially with `node_modules/` containing thousands of files) but also meant those files were explicitly marked for preservation during rewind. Now they are excluded from session state entirely, which solves the bloat problem.

- **Rewind deletion loop**: Previously, the `filepath.Walk` during rewind would visit every file on disk, including gitignored ones. However, gitignored files would pass through the "is it in checkpoint?" check (no), the "is it tracked in HEAD?" check (no), and the "was it in UntrackedFilesAtStart?" check (yes, because the old `collectUntrackedFiles` captured them). So under the old code, gitignored files were NOT deleted during rewind -- they were protected by appearing in `UntrackedFilesAtStart`. Under the new code, gitignored files are not visited at all during rewind (because `gitUntrackedFiles()` excludes them). The end result is the same: gitignored files survive rewind. The mechanism is different (exclusion by omission vs. explicit preservation), but the outcome is equivalent.

- **Edge case -- `.gitignore` changes during session**: If the user's agent modifies `.gitignore` during a session (e.g., adding an ignore rule for a file the agent created), that file would become invisible to the rewind deletion logic and would survive rewind. Under the old code, the file would also survive because it would have been captured in `UntrackedFilesAtStart` (if it existed at session start) or the walk would find it and potentially delete it. This is a subtle behavioral difference, but in practice it is benign: if the agent added a gitignore rule for its own file, preserving that file during rewind is probably the correct behavior.

- **Edge case -- gitignored files created by the agent**: If the agent creates a file that happens to be gitignored (e.g., a `.log` file in a repo that ignores `*.log`), the old code would have deleted it during rewind (since it was not in `UntrackedFilesAtStart` and not in the checkpoint). The new code will NOT delete it (because `git ls-files --others --exclude-standard` will not list it). This is a genuine behavioral difference. However, the new behavior is arguably more correct: deleting gitignored files is surprising to users, and the new tests explicitly validate this preservation behavior.

**Verdict on behavioral change**: The change from "walk everything, protect known files" to "only see git-visible files" is a sound architectural decision. It aligns the CLI's model of the filesystem with git's model, which is the correct abstraction level for a git-focused tool. The primary benefit (avoiding walks through enormous gitignored directories like `node_modules/`) is significant for real-world performance. The risk of the edge cases described above is low and the new behavior is more intuitive.

**Git CLI dependency**: The change adds one more `exec.CommandContext` call to the git CLI. The `git ls-files` command is stable, universally available wherever git is installed, and fast (it reads the index and does stat calls, but respects gitignore rules natively). The CLI tool already requires git to be installed (it uses `git rev-parse`, `git reset`, `git branch`, `git show-ref`), so this adds no new external dependency.

**No unit tests for `gitUntrackedFiles` itself**: The function is tested indirectly through the integration tests, which validate end-to-end behavior including the gitignore filtering. However, there is no unit test for `gitUntrackedFiles()` in isolation (e.g., testing the `isProtectedPath` filtering, empty output handling, or error propagation). The existing `collectUntrackedFiles` also had no unit tests, so this is not a regression -- but it is a missed opportunity.

### Question 1: Should `collectUntrackedFiles` be removed?

`collectUntrackedFiles()` is now a trivial wrapper:

```go

```

It has exactly one caller: `manual_commit_session.go:213`. The wrapper adds no logic, no filtering, and no value.

**Recommendation: Keep the wrapper, but for the right reason.** The function name `collectUntrackedFiles` communicates intent at the call site (line 213 of `manual_commit_session.go`): "capture untracked files for session state." The name `gitUntrackedFiles` communicates mechanism: "call git to list untracked files." At the session initialization call site, the intent-based name reads better. This creates an inconsistency: three call sites doing the same logical operation use two different function names. If `collectUntrackedFiles` is the intended API, then `Rewind` and `PreviewRewind` should call it too. If `gitUntrackedFiles` is the intended API, then `collectUntrackedFiles` should be removed.

**Concrete suggestion**: Either (a) have all three call sites use `collectUntrackedFiles()` for consistency and keep `gitUntrackedFiles` as an unexported implementation detail that only `collectUntrackedFiles` calls, or (b) remove `collectUntrackedFiles` entirely and have all three sites call `gitUntrackedFiles` directly.
