# Store Stripped Transcripts in MySQL

## Context

The transcript pipeline has a GitHub API bottleneck. Today, transcripts (`full.jsonl`) are fetched from GitHub in three places:
1. **Search indexing** (`processSearchIndexBatch`) — fetches per-checkpoint via REST on every index
2. **Transcript endpoint** (`/checkpoints/:id/transcript`) — fetches from GitHub on KV cache miss (first user click)
3. **Backfills** — repo sync discovers checkpoints but never fetches transcripts; search indexing does it later

By storing stripped transcripts in MySQL at webhook time, all downstream consumers (search, UI, backfill) read from the DB. GitHub API calls for transcripts drop to zero after initial ingest.

The Python `strip-transcript.py` script reduces JSONL by ~60-80% by keeping only fields the parsers actually read — making DB storage practical.

## Architecture Decision: No New Queue

We already have `SEARCH_INDEX_QUEUE`. Today it: fetches checkpoints from DB → fetches transcripts from GitHub → indexes to Turbopuffer. The change: fetch transcript from GitHub → strip → store in DB → index to Turbopuffer (using DB transcript). Same queue, same trigger points, just adds a DB write step. No new queue needed.

For backfill of newly connected repos, `repo-sync-service` already queues to `SEARCH_INDEX_QUEUE` — we just need to make sure it does so consistently. The search index queue handler becomes the single place where transcripts are fetched from GitHub and stored.

## Schema: New Column on `repo_checkpoints`

**Why not a separate table?** The transcript is 1:1 with a checkpoint. A separate table adds JOIN complexity and a second upsert in every write path. A LONGTEXT column on the existing table keeps things simple. MySQL stores LONGTEXT off-page, so it doesn't affect queries that don't SELECT it. We just need to avoid `SELECT *` in hot paths (already the case — all queries use explicit column lists).

**Storage format: per-session JSON map.** Multi-session checkpoints store each session's stripped JSONL separately, matching the GitHub folder structure:
```json
{"0": "...stripped session 0 jsonl...", "1": "...stripped session 1 jsonl..."}
```
This makes it easy to serve individual sessions and matches the `0/full.jsonl`, `1/full.jsonl` structure on GitHub.

**New file: `api/src/lib/strip-transcript.ts`**

Port of `strip-transcript.py`. Core function:

```typescript
export function stripTranscript(jsonlContent: string): string
```

- Processes line-by-line (no full parse into memory)
- Drops entry types: `progress`, `file-history-snapshot`, `queue-operation`, `system`
- For `assistant`: keeps `type`, `timestamp`, `message.id`, `message.content` (drops thinking blocks, tool_use `caller`)
- For `user` tool_result: keeps `type`, `content[].tool_use_id`, `toolUseResult.{type,file,error,answers}`
- For `user` text: keeps `type`, `timestamp`, `uuid`, `message.content`
- Returns JSONL string (newline-separated)
- Agent-agnostic: the stripping targets the common JSONL superset. Non-Claude agents that use different entry types just pass through user/assistant entries

### 4. Transcript Endpoint: DB-First with GitHub Fallback

**Modify: `api/src/routes/cache.ts`** (transcript endpoint, ~line 2585)

New flow:
```
Request → KV cache hit? → return cached
        → DB has transcript_stripped? → parse + return (+ cache to KV)
        → GitHub fallback (existing code) → return (+ cache to KV)
```

The DB lookup is a simple query: get `transcript_stripped` and `sessions` JSON from `repo_checkpoints` where `checkpoint_id = ?`. The `sessions` column already has per-session metadata (agent, sessionId, tokenUsage, attribution, transcriptIdentifierAtStart).

For multi-session checkpoints: the `transcript_stripped` JSON column contains `{"0": "...jsonl...", "1": "...jsonl..."}`. The `sessions` JSON column has per-session metadata (agent, sessionId, tokenUsage, attribution, transcriptIdentifierAtStart). The transcript endpoint iterates sessions, pulls the JSONL for each index from the map, and parses with the appropriate agent parser — same as today's GitHub fetch loop but from a single DB read.

**Important**: The stripped transcript preserves all fields the parsers read, so existing parsing code works unchanged.

// Hash checkpoint_id to a deterministic numeric ID for Turbopuffer
// Uses two FNV-1a 32-bit hashes (different seeds) combined into a 53-bit integer
// to stay within Number.MAX_SAFE_INTEGER while avoiding birthday-paradox collisions
// (50% collision probability at ~94M entries vs ~77K with 32-bit)
export function hashToNumericId(checkpointId: string): number {
  // First hash: standard FNV-1a 32-bit
  let h1 = 0x811c9dc5;
  for (let i = 0; i < checkpointId.length; i++) {
    h1 ^= checkpointId.charCodeAt(i);
    h1 = Math.imul(h1, 0x01000193);
  }
  h1 = h1 >>> 0;

  // Second hash: FNV-1a with different offset basis
  let h2 = 0x050c5d1f;
  for (let i = 0; i < checkpointId.length; i++) {
    h2 ^= checkpointId.charCodeAt(i);
    h2 = Math.imul(h2, 0x01000193);
  }
  h2 = h2 >>> 0;

  // Combine: 21 bits from h2 (high) + 32 bits from h1 (low) = 53 bits
  return (h2 & 0x1fffff) * 0x100000000 + h1;
}
